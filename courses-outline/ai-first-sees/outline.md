## S01 · hook — 三个画面

- **时长**：50s
- **一句话论题**：AlphaGo、ChatGPT、会操作电脑的 Agent，是三次不同的跃迁。
- **屏幕文字**：2016 / 2022 / 2026；看 → 说 → 做
- **画面**：三联屏。左：围棋棋盘，最后一子落下；中：一个干净的聊天框，光标闪烁；右：一台笔记本电脑，鼠标自己移动，文件被打开、代码被修改。三联屏底部各放一个小 Logo：左 DeepMind、中 ChatGPT、右 OpenClaw / WorkBuddy / DSH。
- **动画**：三块画面依次亮起，每块只停留 2 秒；最后三块并排，中间出现一条时间轴。棋盘上的棋子用“落子”动画，聊天框用“打字”动画，电脑用“光标自己移动 + 文件树展开”动画。这个时间轴从 2016 到 2026 整整十年间缓慢推进，能看到时间的推移，还有这几个画面的出现。
- **旁白**：
  > 2016 年，一台机器在围棋上赢了李世石。6 年后，也就是 2022 年，一个聊天框让所有人第一次觉得，AI 什么都能聊。4 年后，2026 年，AI 不再只是回答你，它开始自己打开文件、写代码、跑命令。今天，我们要讲的就是 AI 的 10 年发展历程，以及如何把当前的 AI 用好。
  >
- **事实/口径**：2016-03 AlphaGo 4:1 李世石；2022-11-30 ChatGPT 上线；2026 年 OpenClaw/WorkBuddy 出圈。
- **素材**：棋盘 SVG、聊天框组件、笔记本/文件树 SVG；`./素材/logo/deepmind.png`、`./素材/logo/chatgpt.png`、`./素材/logo/openclaw.png`、`./素材/logo/workbuddy.png`、`./素材/logo/dsh.png`；不用机器人 stock photo。

- **屏幕文字**：看 → 说 → 做 → 用；上半场 / 下半场

  > AI 这 10 年的历程，可以总结为四个字：看、说、做、用。十年前，AI 学会了看，学会了理解；后来，它学会了说，学会了生成文字；现在，它学会了做，从只读变成了可读可写，这是 AI 能力的跃迁。而我们要学的，是怎么用好它。

## S03 · alphago — 机器第一次赢在“直觉”

- **时长**：40s
- **一句话论题**：AlphaGo 赢的不是算力，是“看棋形 + 推演 + 自练”的组合。
- **屏幕文字**：2016.03 / 首尔 / AlphaGo 4:1 李世石 / 五番棋 = 五局定胜负 / DeepMind
- **画面**：棋盘俯视，黑白子逐渐填满；镜头推到一角，棋子变成发光的“棋形”；旁边浮出三个小标签：看、想、练；右侧记分牌写清“AlphaGo 4 : 1 李世石”，记分牌下方补一行“五番棋 = 五局定胜负；李世石赢下第 4 局”；右下角放 DeepMind Logo，旁边是当年的现场照片。
- **动画**：先落子（每 0.4s 一子），再推近；三个标签依次亮起；“4:1”从记分牌翻出，同时现场照片淡入，随后补出五番棋说明。
- **旁白**：
  > 2016 年 3 月，首尔。DeepMind 的 AlphaGo 以 4 比 1 战胜李世石。这场比赛为什么震动？因为围棋长期被认为是“人类直觉的最后堡垒”。棋盘的变化比宇宙原子还多，机器不是靠穷举赢的。它是靠“看”，看棋形；靠“想”，推演几步；靠“练”，自己跟自己下。
  >
- **事实/口径**：DeepMind 2014 年被谷歌收购；2016-03-09 至 03-15，五番棋（五局定胜负），AlphaGo 4:1 李世石，李世石赢下第 4 局；不要写成“李世石 4:1”。AlphaGo 使用 CNN 策略/价值网络 + MCTS + 监督学习/强化学习。不要讲成“纯 CNN”。

## S04 · cnn — 一层一层的滤镜

- **时长**：90s
- **一句话论题**：CNN 不写规则，它从数据里学“特征”；它的工业拐点是 2012，不是 2016。
- **屏幕文字**：像素 → 边缘 → 形状 → 物体；2012 AlexNet；26.2% → 15.3%
- **画面**：左边一张真实猫照片（先像素化），右边四层“滤镜”依次抽出：第一层只有边缘，第二层有耳朵/胡须的轮廓，第三层有眼睛，第四层拼成一只猫。下方一条应用带：医疗影像、工业质检、人脸、OCR；讲到 AlphaGo 时，再贴上 AlphaGo 赢李世石和柯洁的两张照片，右下角带 DeepMind Logo。
- **动画**：像素图先马赛克化，再逐层“清晰”；每层滤镜用半透明色块扫过；应用带从右往左滑入。
- **旁白**：
  > 10 年前，AI 主要的能力是它“看”的本事，这个能力来自于卷积神经网络，CNN。你可以把它想成一层一层的滤镜：第一层看边缘，第二层看形状，第三层看眼睛、耳朵，最后拼成一只猫。以前我们写规则：“有尖耳朵、有胡须、有尾巴”，但真实世界太复杂，规则写不完。CNN 换了个办法：不写规则，给你看几百万张图，让它自己学特征。这件事的拐点其实不是 2016，是 2012 年。AlexNet 在 ImageNet 比赛上把 Top-5 错误率从 26.2% 降到 15.3%，从那以后，CNN 进了医院、工厂、手机和摄像头。AlphaGo 只是让大众更全面地了解到这个技术的能力。
  >
- **事实/口径**：AlexNet 2012，ImageNet Top-5 错误率 26.2% → 15.3%；CNN 不是 AlphaGo 发明的。应用例子是示意，不声称“所有行业都用 CNN”。
- **素材**：猫图用 `./素材/photo/cat.jpg`（CC0，Wikimedia Commons，作者 AdinaVoicu）做像素化处理；滤镜层用 SVG + 半透明遮罩；应用图标用线性图标；`./素材/photo/alphago-lee-sedol.webp`、`./素材/photo/alphago-ke-jie.jpg`、`./素材/logo/deepmind.png`。

## S05 · gpt1 — 文字接龙

- **时长**：30s
- **一句话论题**：语言模型的底层任务简单到不可思议：猜下一个词。
- **屏幕文字**：2018 / GPT-1 / 117M / “下一个词是？”
- **画面**：一句话：“今天天气真___”；下方一排候选词：好、冷、热、蓝……概率条依次出现；镜头拉远，看到“117M”像一块小牌子；右上角放 OpenAI Logo。
- **动画**：候选词逐个出现，概率条从 0 长到对应长度；“好”被选中，句子补全；然后画面切到“117M”。
- **旁白**：
  > 但“会看”不等于“会说”。语言模型走的是另一条路。它的任务简单到不可思议：给你一句话，猜下一个词。2018 年，OpenAI 的 GPT-1 只有 1.17 亿个参数，它做的事就是文字接龙。你今天觉得 ChatGPT 很聪明，但它的底层动作，仍然是接龙，只是接得非常好。
  >
- **事实/口径**：GPT-1 2018-06，117M 参数；底层是 Transformer decoder；不要讲成“GPT-1 就是 ChatGPT”。
- **素材**：文字动画；概率条；117M 数字牌；`./素材/logo/openai.png`。

## S06 · scaling-emergence — 规模定律与涌现

- **时长**：210s
- **一句话论题**：任务没变，规模变了；能力不是慢慢长上去的，是在跨过某个门槛之后突然出现的。
- **屏幕文字**：2019 GPT-2 1.5B / 2020 GPT-3 175B；Scaling Law；Emergent Abilities；三位数加法 <10% → 80%；量变引起质变
- **画面**：一张主图贯穿整屏：横轴是模型规模（对数刻度：1.25 亿、3.5 亿、7.6 亿、13 亿、27 亿、67 亿、130 亿、1750 亿），纵轴是准确率。先出现一条平滑上升的曲线（规模定律）；然后画面切到“多位数加法”，曲线在 130 亿之前贴着地面，到 1750 亿突然竖起来，形成一个“台阶/悬崖”。台阶右侧打上“Emergent Abilities”标签。第三段插入一个小对比：左边 1.3B InstructGPT，右边 175B GPT-3，人类偏好投票小模型胜出。最后画面底部滑出一条细时间轴：2017 Transformer → 2018 BERT → 2020 GPT-3 → 2021 悟道 2.0 → 2023 文心一言/通义千问/ChatGLM → 2024–2025 DeepSeek/Kimi。
- **动画**：① 三根柱子从低到高（117M → 1.5B → 175B），背景曲线随柱子显现；② 曲线切换成加法准确率：前七个点依次落在贴近 0 的位置，最后一个点“弹”到 80%，伴随一次短促的镜头推近；③ 台阶定格，标签淡入；④ 投票条从左往右长，小模型那侧超过大模型；⑤ 底部时间轴从左往右生长，中国节点用另一种颜色。全程只用一个运动焦点，不要同时动。
- **分镜节拍**：

| 节拍 | 时间      | 画面                                                              | 旁白落点                               |
| ---- | --------- | ----------------------------------------------------------------- | -------------------------------------- |
| 1    | 0–35s    | GPT-2 生成一段很像人写的文字，旁边是“它能干活吗？”的问号        | 2019 年就有 GPT-2，为什么大家没感觉    |
| 2    | 35–75s   | 三根柱子 + 平滑上升的规模曲线                                     | 任务没变，规模变了；规模定律是可预测的 |
| 3    | 75–125s  | 多位数加法的“悬崖”图，13B 贴地、175B 跳起                       | 能力不是线性增长，是涌现               |
| 4    | 125–170s | 1.3B InstructGPT vs 175B GPT-3 的人类偏好投票                     | 规模之外，还有对齐                     |
| 5    | 170–210s | 底部时间轴：Transformer/BERT/悟道/文心/通义/ChatGLM/DeepSeek/Kimi | 不是 OpenAI 一家的独角戏               |

- **旁白**：

  > 大语言模型不是 2022 年才发明的，学界研究了很多年。2019 年，OpenAI 放出 GPT-2，15 亿参数。它写出来的文字已经很像人了，但当时并没有引起太多的关注，因为他的能力还不够出众，无法满足我们日常的工作。2020 年，GPT-3 来了，1750 亿参数，任务还是同一个：猜下一个词。OpenAI 发现，模型越大、数据越多、算力越多，能力会按一条相当稳定的曲线往上走。这就是 scaling law，规模定律。直白的说就是“大力出奇迹”。
  >
  > 真正让人意外的，是另一件事。GPT-3 的论文里有一组多位数加法的实验：从 1.25 亿到 130 亿参数的模型，三位数加法基本都在 10% 以下，跟瞎猜差不多；可一跨过 130 亿这个门槛，到 1750 亿，准确率一下跳到 80%。两位数加法更明显：130 亿那一档只能对一半，1750 亿接近全对。不是慢慢变好，是在某个门槛上，突然就会了。2022 年，有研究把这个现象命名为“涌现能力”，Emergent Abilities：有些能力，在小模型上根本看不到，模型大到一定程度，它突然就出现了。用一句话说，就是量变引起质变。这也是为什么，GPT-2 时代大家没感觉，GPT-3 之后，很多人觉得：大语言模型的智商非常的高。
  >
  > 大语言模型不是 OpenAI 一家的独角戏。2017 年，谷歌的 Transformer 铺好了路；2018 年，BERT 证明了预训练的力量；2021 年，国内的悟道 2.0 进了万亿参数俱乐部；2023 年，文心一言、通义千问、ChatGLM 接连发布；后面还有 DeepSeek、Kimi。
  >
- **事实/口径**：GPT-2 1.5B（2019-02）；GPT-3 175B（2020-05）；scaling law 论文 2020-01；GPT-3 论文 Figure 3.10：三位数加法，13B 及以下模型准确率低于 10%，175B 约 80.4%；两位数加法 13B 约一半、175B 接近满分。涌现能力论文 2022（Wei 等，arXiv:2206.07682），定义是“小模型没有、大模型出现的能力”；“涌现是海市蜃楼”论文 2023（arXiv:2304.15004）指出部分“突然”可能是评测指标造成的。InstructGPT 2022，1.3B 在人类偏好上优于 175B GPT-3，这是特定评测，不是“1.3B 全面强于 175B”。悟道 2.0 2021-06，1.75 万亿（稀疏）；文心一言 2023-03-16；通义千问 2023-04-11；ChatGLM-6B 2023-03-14；DeepSeek-V3 2024-12；Kimi K2 2025-07。不要展开 benchmark。

## S09 · l3-agent — 给 AI 套一层行动循环

- **时长**：70s
- **一句话论题**：补全是“猜下一行”，Agent 是“做一步、看结果、再决定下一步”。
- **屏幕文字**：2023.03 Cursor / 2024.11 Agent 模式 / ReAct / Function Calling
- **画面**：左边代码编辑器，光标补全一行；右边同一个编辑器，Agent 自己打开三个文件、改代码、跑测试、看到红色报错、再改；中间一个循环图：观察 → 思考 → 行动 → 观察。编辑器右上角放 Cursor Logo；讲到 Agent 模式时，旁边浮出 Cursor 真实界面截图。
- **动画**：左边只补一行；右边文件树依次展开，diff 逐行出现，测试窗口变红再变绿；循环图旋转，箭头流动；Cursor 截图在讲到“Agent 模式”时淡入，然后缩小到角落。
- **旁白**：
  > 第三阶段，变化发生在程序员这边。Cursor 最早只是代码补全，2023 年 3 月上线；到 2024 年 11 月，它有了 Agent 模式。区别在于，补全，是你写一行，它猜下一行；Agent，是你给它一个目标，它自己读文件、改代码、跑测试，看到报错再改。给 AI 套一层循环，它就从“工具”变成了“数字工人”。这个循环，学术界 2022 年就有个名字，叫 ReAct：推理、行动、观察，再推理。2023 年，OpenAI 又把 function calling 做成了标准接口。循环加工具，Agent 的大门就打开了。

- **事实/口径**：Cursor 2023-03-14 上线；Agent 模式 2024-11-24；ReAct 2022；OpenAI function calling 2023-06-13。

## S12 · harness-anatomy — 一个完整能力的办公工位

- **时长**：85s
- **一句话论题**：Harness 的四件套是工具、Skill、MCP、行动循环；外面还有上下文和权限。
- **屏幕文字**：工具 = 办公设备 / Skill = 岗位 SOP / MCP = 跨部门接口 / 行动循环 = 工作闭环 / 权限 = 岗位权责
- **画面**：空办公工位 → 配齐设备的工位 → 连上公司系统 → 循环处理工单；桌面标出四个核心部件，外围标出“文件柜”和“权限牌”。
- **动画**：先出现空工位；摆上电脑、打印机、键盘（工具项依次亮起）；放上岗位 SOP 手册与流程图示（Skill 亮起）；工位系统同时连上财务、人事、业务系统（MCP 亮起，多系统连线）；“接需求 - 处理 - 交付 - 反馈”四步循环流动（行动循环亮起）；最后外围浮现历史档案柜和岗位权限牌。
- **旁白**：
  > 把 Harness 看成一个员工的工位。工具，是纸、笔、电脑、打印机、键盘这些设备，是员工干活的工具；Skill，是岗位 SOP 和作业手册，告诉他每件事的标准流程；MCP，是跨部门的系统接口，让他能和财务、业务所有体系打通协作；行动循环，就是“接需求 - 处理 - 交付 - 反馈”的工作闭环，是他持续运转的节奏。上下文是工作日志和档案，决定他“记得什么”；权限是岗位权责和审批等级，决定他“能碰什么”。四件加两层，就是 Harness 的完整组成。而真正办公的人，就是 Harness 对接的大脑；这个工位可以有不同智力的员工入座：聪明的员工相当于能力更强的模型，不聪明的员工相当于能力相对较弱的模型。他们都可以在这个工位里干活，干活的好坏，取决于员工的聪明程度，也就是模型的能力强弱。其实 harness 是一个工程学问题，目前各大厂家提供的工位能力都差不多，而决定 harness 强弱的是这个工作流程及工作准则
  >
- **事实/口径**：这是教学比喻；Harness 的工程定义见 Microsoft Learn：“runtime scaffolding that turns a language model into an agent”。
- **素材**：工位 + 电脑 + 纸 + 笔 + 鼠标 + 键盘 + 档案手册（Skill） + 行为准则。

## S13 · tools-skills-mcp — 说到底，都是喂给模型的文字

- **时长**：100s
- **一句话论题**：工具、Skill、MCP 看着是三种能力，本质都是提前把一段文字注入给模型。
- **屏幕文字**：工具 = 固定格式 / Skill = 固定流程 / MCP = 统一接口；模型只能读文字
- **画面**：左边一个“模型”对话框；右边三个投喂口，每个口子往模型里送一段文字：
  1. 工具卡片：`write_file(path, content)` → `ok`，上面写着“固定格式、固定返回”；
  2. Skill 小册子：`SKILL.md`，封面写“这类活怎么做”，里面是步骤、注意事项、脚本；
  3. MCP 接口面板：外部软件（数据库、日历、画图软件）按同一个格式登记自己的能力，Agent 通过接口调用。
- **动画**：三张卡片依次飞进模型左侧的“上下文”入口；每飞入一张，模型右侧就多一个能力图标；最后三张卡片合在一起，变成一行字：“都是文字”。MCP 卡片上出现“接口”两个字，不出现 USB-C 之类的比喻。
- **旁白**：
  > 工具、Skill、MCP，名字不一样，但有一件事是一样的：它们最后都得变成一段文字，塞进模型的上下文里。因为模型只能读文字。工具，是一个固定格式：我告诉你，你可以调用 write_file，参数是路径和内容；你按这个格式说，我替你去执行，再把结果以文字还给你。Skill，是一段固定流程：把我做这类事的经验写成一份说明书，需要的时候整段喂进去，模型照着做。MCP，是一个统一的接口：外部软件按同一个格式，把自己的能力登记成工具说明书，Agent 就能接上它。你可以把它们理解成三种“提前写好的提示词”：工具是格式，Skill 是流程，MCP 是接口。所以 Harness 的能力边界，很多时候不取决于模型多聪明，而取决于你提前给它喂了什么。
  >
- **事实/口径**：现代 API 用结构化的 `tool_calls`，不是让模型直接输出一段裸 JSON 文本，教学上简化为“固定格式的结构化意图”；Skill 常见格式是 `SKILL.md` + YAML frontmatter（name/description），可带脚本/资源；MCP 是开放协议（JSON-RPC），服务器可暴露 tools/resources/prompts；工具结果、Skill 内容、MCP 工具描述最终都以文本形式进入上下文。不要把 MCP 说成 Skill，也不要用 USB-C 比喻。
- **素材**：自绘卡片、上下文入口、接口面板；`./素材/logo/mcp.png`（若可用）；代码/文件名用等宽字体。

## S17 · stateless-notebook — 只认笔记本的专家

- **时长**：98s（已上线课程 98.2s）
- **一句话论题**：大模型 API 默认无状态；记忆不在模型里，在 Harness 用上下文拼出来的那本笔记本里。
- **屏幕文字**：同一个对话：换了模型 / 断了网 / 过了一夜；模型 API 默认无状态；一本笔记本 = 一次会话；上下文窗口 100 万 vs 21 万 token；记忆在 Harness，不在模型

  > 先问一个你肯定遇到过的问题：你换一个模型，对话还能接着聊；网断了重连，记录还在；第二天打开，它还记得昨天聊到哪。可大模型的 API，默认是「不记得你」的。那这些记忆，到底存在哪？
  >
  > 你可以把大模型想成一个黑屋里的专家。屋子很小，只有一张桌子、一盏灯、一个窗口。专家非常聪明，但他不认人，只认笔记本。门外排着成千上万的人，每人手里一本笔记本。
  >
  > 每一本笔记本，就是一次会话。第一页是 Harness 写的系统提示词：你是谁、能做什么、不能做什么。后面是你们聊过的每一句话，中间还夹着工具返回的结果。专家每次拿到本子，都从第一页开始读，一直读到最后一页，然后在下一页写下答案，合上，递出去。下一个本子进来，他又是从头开始。
  >
  > 现在你就能解释那三件事了。换模型，就是把同一本笔记本，递给另一个专家；断网，就是笔记本一直在你手里，重新递进去就行；那为什么长对话越来越贵？因为每问一次，专家都要把整本从头读一遍。而且，每个专家一次能读完、记住的厚度是有限的，这就是上下文窗口，有的模型能读 100 万 token，有的只有 21 万。本子太厚，前面的内容就得压缩、丢掉。所以真正的记忆不在模型里，在 Harness 帮你整理的这本笔记本里。
  >
- **事实/口径**：API 默认无状态；但产品层可以存会话（ChatGPT 网页、Responses `store` 等）。旁白说“API 默认”，留了口子；不要绝对说“所有大模型都不存会话”。上下文窗口有上限；旁白里的“100 万 / 21 万 token”是课程口径举例（不同模型窗口不同，讲课前复核）；压缩会丢细节，不要说成“模型记住了”。时长、旁白与画面按已上线课程回写。

## S18 · long-session — 长会话不是免费的记忆

- **时长**：100s
- **一句话论题**：每轮都要把整本上下文重放一遍，token 越滚越多，长会话越聊越贵；所以一任务，一会话。
- **屏幕文字**：第 20 轮 = 前 19 轮全量重放；token 越滚越多；一任务，一会话
- **画面**：一本笔记本越来越厚；每翻一页，旁边一个 token 计数器往上跳；最后出现一条“累计 token”曲线。镜头拉远，桌上多出一本干净的新笔记本，旧本子被推到一边，新本子第一页写着这次任务的名字。
- **动画**：笔记本逐页变厚；计数器数字快速上涨；曲线从线性变成上翘；定格在一个具体数字例子；新本子滑入画面，五张“什么时候该新开”的小卡片依次翻开，最后收拢成一句话“一任务，一会话”。
- **旁白**：
  > 但代价也在这里：你聊到第 20 轮，第 20 次请求带的，是前 19 轮的全部内容——每答一次，专家都要从头读一遍。所以长会话不是“免费的记忆”，而是“每一轮都重新买一遍”。这就是为什么，很多人问一个小问题，还挂在原来的长会话里，token 会烧得很快。
  >
  > 所以，第一个使用习惯：一任务，一会话。新任务，新会话；旧上下文和新问题无关，新会话；会话太长、或者上下文窗口快满了，先总结再新开；换模型、换供应商，想干净一点就新开；舍不得丢的结论，让 Agent 先写一份 handoff，再新开。一句话：一任务，一会话。可有些任务天生就长，中途没法换本子，那本子写满了怎么办？
  >
- **事实/口径**：实际计费还涉及系统提示、工具 schema、检索内容、缓存等；这里只讲“全量重放”的主因。数字例子：每轮新增 500 token，20 轮累计约 10.5 万 token。新开会话是经验规则，不是硬性标准；不同 Harness 的上下文管理/压缩策略不同。
- **素材**：笔记本、token 计数器、曲线、五张卡片、handoff 模板。

## S19 · compact — 写满的笔记本，压成一页纸

- **时长**：105s
- **一句话论题**：上下文窗口是有限的；快写满时，Agent 会把整本笔记本压成一页纸，贴进一本新本子。
- **屏幕文字**：上下文窗口 / 快写满了 / Agent 自己压缩 / 一页纸 / 会丢信息
- **画面**：还是 S17 那间黑屋。桌上的笔记本已经厚到合不上；专家翻到一半，手停下来，灯光也像暗了一格——他的精力和记忆是有限的，超出这个厚度的页，他读不完，也记不住。窗口上方的“厚度尺”爆表，超出的页被挡在窗口外面。这时画面里伸出一只手（Agent 的手）：把旧本子摊开，在全新的一页纸上写下几句“这个本子讲了什么”，撕下这一页，贴进一本刚拆封的新笔记本，只占第一页。新本子从传递窗递进去，专家很快读完，继续写答案。旧本子合上，放进旁边的档案柜，不销毁。
- **动画**：笔记本逐页加厚 → 厚度尺超过刻度、亮红 → 专家翻页变慢、停在中间 → 一页摘要从旧本子里“长”出来（文字逐行提炼）→ 摘要粘进新本子 → 新本子递进窗口 → 专家快速翻完、落笔 → 最后一行小字：“压缩由 Agent 自动触发”。
- **分镜节拍**：

| 节拍 | 时间     | 画面                               | 旁白落点                               |
| ---- | -------- | ---------------------------------- | -------------------------------------- |
| 1    | 0–25s   | 厚到合不上的笔记本，专家越翻越慢   | 专家的精力、记忆都是有限的             |
| 2    | 25–50s  | 厚度尺爆表，超出的页读不进去       | 超出窗口的部分，专家根本读不到         |
| 3    | 50–75s  | Agent 把整本提炼成一页，贴进新本子 | 这就是上下文压缩                       |
| 4    | 75–105s | 新旧两本对照，一些句子在摘要里消失 | 压缩由模型自己判断，重要的信息也可能丢 |

- **旁白**：
  > 本子写满了，就压缩——因为上下文窗口是有上限的。你想想专家的处境：他每一次都要从第一页读到最后一页；本子越厚，他读得越慢，忘得也越多。他的精力和记忆都有上限——一旦本子厚过这个上限，后面的页他就读不到，更谈不上理解。
  >
  > 这时候，Agent 会自己动手：把整本笔记本摊开，用一页纸，把这个本子里最核心的论点写下来——做过什么、定了什么、还剩什么没做完；然后把这一页贴进一本全新的笔记本，当作新的材料，再递进去。这就是上下文压缩，compaction。新本子很薄，专家一眼读完，又能继续干活。
  >
  > 但你要知道代价：这一页纸是模型自己总结的。它认为不重要的一句话，可能恰恰是你最在意的——某条规矩、某个数字、某句“这个目录不要动”，都可能在压缩时被抹掉。压缩能救急，不能当记忆用；真正不能丢的东西，要写进你自己能控制的地方。
  >
- **事实/口径**：上下文窗口有上限；上下文压缩（compaction / auto-compact）通常由 Harness 在接近窗口上限时自动触发，把历史摘要成更短的上下文再继续对话；不同产品的触发阈值、摘要方式不同；摘要由模型生成，会丢细节，不保证保留人认为关键的信息。不要说成“模型记住了”。
- **素材**：回收 S17 的黑屋、专家、传递窗；更厚的笔记本；一页摘要；全新的笔记本；厚度尺；档案柜；可选 `./素材/screenshot/dsh-desktop.png`（标出上下文拼接/压缩的位置）。

## S20 · agents-md — 给 AI 一个项目记忆

- **时长**：95s
- **一句话论题**：项目的事写进工作区的 agents.md，个人的习惯写进全局记忆；AI 每次开工前先读它。
- **屏幕文字**：AGENTS.md / 项目记忆 / 全局记忆 / 约定俗成
- **画面**：三栏递进。
  - 左：新会话窗口，用户又在打一段很长的项目背景：“这个项目是……我们的目标是……不要动 xxx 目录……”；旁边堆起一摞写满同样内容的纸，越堆越高。
  - 中：工作区根目录出现一个 `AGENTS.md` 文件，像一本“项目手册”立在门口；AI 推门进来，先拿起手册读；之后每开一个新会话，手册自动被带上，纸堆消失；画面一角可嵌入 `agents.md` 官网截图（“60k+ open-source projects”“One AGENTS.md works across many agents”），作为“约定俗成”的证据。
  - 右：全局记忆。两栏对比：项目级（`AGENTS.md`：项目背景、目标、目录结构、常用命令、禁止事项）和全局级（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`、`memory.md`：永远用中文回答、不要自动 commit 这类个人习惯）。
- **动画**：重复解释的纸越堆越高 → `AGENTS.md` 出现，纸堆被吸进文件 → AI 进门先读手册 → 镜头拉到全局层，全局文件亮起 → 最后两栏并排，中间一条线，左边写“项目”，右边写“习惯”。
- **旁白**：
  > 还有一件很烦的事：每开一个新会话，你都要重新解释一遍——这个项目是干什么的、最终要做什么、哪些目录不能动。说一遍两遍还行，说十遍就受不了了。办法其实很简单：在工作区根目录放一个 agents.md。它已经是一个约定俗成的文件，Codex、Cursor、OpenCode 这些工具都认它；Claude Code 的 CLAUDE.md，也是同一个道理。你把项目背景、目标、目录结构、常用命令，还有“禁止做什么”写进去；AI 每次开工之前，会先读它。这相当于给 AI 一个项目记忆。
  >
  > 还有一些 Agent 支持全局记忆：比如 Claude Code 的 `~/.claude/CLAUDE.md`，Codex 的 `~/.codex/AGENTS.md`，或者有些工具里的 memory.md。像“永远用中文回答”“不要自动 commit”这种跨项目都成立的偏好，就写在全局里。项目的事写项目里，个人的习惯写全局里。
  >
- **事实/口径**：AGENTS.md 是开放格式，由 Agentic AI Foundation（Linux Foundation）托管；Codex、Cursor、OpenCode、Gemini CLI、Windsurf、Devin 等工具支持；放在仓库根目录，子目录可以放嵌套的 AGENTS.md，最近的优先。Claude Code 默认读 `CLAUDE.md`（项目级）和 `~/.claude/CLAUDE.md`（用户级），也可以通过导入/配置兼容 AGENTS.md；Codex 的项目级是 `AGENTS.md`，用户级是 `~/.codex/AGENTS.md`。DSH 也读 `AGENTS.md`；开箱只记住一个会话内的事，跨会话长期记忆需要记忆插件。不要把“agents.md”写成某个工具专属。
- **素材**：自绘：新会话窗口、纸堆、`AGENTS.md` 手册、门、两栏对比；文件路径用等宽字体；可用本仓库真实的 `AGENTS.md` 片段做画面内容（节选“不可协商”两三条）；`./素材/screenshot/agents-md-site.png`（agents.md 官网截图，自截）。

## S21 · agents-md-content — 目录的记忆：AGENTS.md 写什么

- **时长**：120s
- **一句话论题**：好的 AGENTS.md 是这个目录的背景、地图和员工守则；写一次，省掉每次重新解释。
- **屏幕文字**：项目概述 / 目录结构 / 编码规范 / 构建与测试 / 文档地图 / 注意事项；PPT 项目：素材 / 背景 / 进度 / 风格
- **画面**：左右两份并排的 AGENTS.md 模板。左边是编程项目，六个条目像六张目录卡；右边是 PPT 项目，四个条目，旁边是素材文件夹、PPT 缩略图和一条进度条。画面下方用“目录 = 房间”的隐喻：门口挂着一本手册，手册里伸出箭头，指向屋里的文档、素材和代码。最后手册翻到新增的一页，红笔写进一条“禁止：动 xxx 目录”，盖上“员工守则”印章。
- **动画**：六张条目卡自上而下逐条落下；镜头右移，切到 PPT 模板；手册从门口取下、翻页；红笔写入新规则；印章盖下，画面定格。
- **分镜节拍**：

| 节拍 | 时间     | 画面                                   | 旁白落点                              |
| ---- | -------- | -------------------------------------- | ------------------------------------- |
| 1    | 0–35s   | 编程项目六张条目卡依次落下             | 一个编程项目的 AGENTS.md 写六块       |
| 2    | 35–65s  | PPT 项目目录：素材夹、背景、进度、风格 | Agent 不只会编程，做 PPT 也要项目记忆 |
| 3    | 65–90s  | 一个目录一本手册，手册指向文档         | 每个目录一份，AI 不用再到处探索       |
| 4    | 90–120s | 手册翻页、红笔加规则、盖章             | 它是活的，是 AI 的员工守则            |

- **旁白**：

  > 那 agents.md 里到底该写什么？如果是一个编程项目，我建议至少写六块。第一，项目概述：这个项目是干什么的，目标是什么。第二，目录结构：哪个目录放什么，哪些目录不能动。第三，编码规范：命名、格式、注释、提交信息怎么写。第四，构建与测试：怎么装依赖、怎么跑起来、怎么跑测试。第五，文档地图：重要的文档放在哪，遇到问题先读哪一份。第六，注意事项：也就是护栏，明确告诉它哪些事不能做。
  >
  > 但 Agent 早就不只是编程工具了。我经常拿它当 PPT 撰写工具。做 PPT 是要素材的，所以我会在项目目录里放一个 agents.md，写清楚四件事：素材汇集在哪个目录、这个项目的背景是什么、现在做到什么进度、这份 PPT 要什么风格。这样下次再让它做这个项目的 PPT，Agent一开始就知道背景，也知道素材去哪儿找，做出来的ppt效果会更好。
  >
  > 所以，不管你是编程、做 PPT，还是做别的事，一个目录下都应该有一份 agents.md。它就是这个目录的记忆：写清楚这个目录是干什么的，再指向相关的其他文档。这样 AI 每次干活，都能很快进入状态，不用花大量时间到处探索，这也是AI时代办公习惯的新变化。
  >
  > 还有一点：agents.md 不是一次写好就不管了。它像写代码一样，要一边干一边想：这件事要不要写进去？AI 踩了坑，或者做出来的东西让你很不满意，就想想是不是该补一条规则，让它写进 agents.md，以后禁止再犯。你可以把它理解成一家大公司的管理规范：正规公司都有详细的制度和禁令，什么能做、什么不能做、事情该怎么做。agents.md 就是你给 AI 在这个目录里定的员工守则。
  >
- **事实/口径**：这六块是经验清单，不是标准，不同项目可以增减；重点不是“写得全”，而是写 AI 每次都要用、且不写就会重复解释的信息。PPT 的四项（素材 / 背景 / 进度 / 风格）是主讲人的工作流，不是唯一模板。不要把 AGENTS.md 写成第二份 README：它能指向 README 和文档，但自己只保留“开工前必须知道”的内容。项目级 AGENTS.md 与全局记忆的分工见 S20。
- **素材**：自绘模板卡、手册、印章；复用 S20 的 `AGENTS.md` 手册与门；；新增 `agents-md-template.png`（自绘模板，待补）。

## S22 · prompt-assembly — 你只问一句，模型读的是一大本

- **时长**：110s
- **一句话论题**：你输入的问题只是最后一行；在它之前，Harness 已经把系统提示、技能列表、MCP 说明拼成了一大段上下文。
- **屏幕文字**：你的问题 < 100 token → 实际请求 1 万–10 万 token；系统提示 / 技能列表 / MCP / 历史
- **画面**：左边一个输入框，用户只打了一句“帮我做个 PPT”；右边是Agent的真实聊天组装，Agent的聊天先把系统提示词组装进聊天中，然后是技能目录描述、MCP 工具说明，Agents.md的文件内容，最后才把用户的聊天内容组装进去，整个画面组装过程像微信聊天窗口那样Agent组装的内容都在聊天的左侧，切入滚动着填充内容，最后用户输入描述从右边切入，类似微信聊天的发件人的角度信息；然后镜头进行一个切换，把右边这个聊天的对话缩小移动到左边，左边原来示意用户输入agent的内容场景离场，把右边原来的聊天缩小并移到左边，形成一个长全景卷轴，然后把这个全景聊天内容框起来。右边显示大模型，然后把全景卷轴发送给这个大模型（用一个动画演示，把那个卷轴作为书本的第一页写入笔记本（和前面场景的笔记本比喻呼应），这本书放到一个纸飞机上飞到大模型哪里（大模型可以用一个戴眼镜的专家形象比喻））。镜头再切到 DSH 的真实界面：轨迹 / 上下文面板里，系统提示、工具 schema、技能说明、消息历史一层层列出来 （局部放大，滚动显示）。
- **分镜节拍**：

想描述的就是用户的一次输入，其实 A 准已经打包了一个长长的对话发给了右边这个大模型。

| 节拍 | 时间     | 画面                                           | 旁白落点                                     |
| ---- | -------- | ---------------------------------------------- | -------------------------------------------- |
| 1    | 0–20s   | 输入框里只有一句话                             | 传给模型的，真的只有这句话吗                 |
| 2    | 20–55s  | agent聊天组装台：系统提示、技能目录、MCP、历史 | Agent 在你按回车前已经拼好一大段             |
| 3    | 55–80s  | token 计数器：80 → 1 万 → 10 万              | 一句话的问题，可能是上万 token 的请求        |
| 4    | 80–110s | DSH 上下文面板，逐层展开                       | 推荐 DSH：整个过程看得见；Harness 就是组装器 |

- **旁白**：

  > 前面讲了这么多，我们在回头想一个问题：你在 Agent 里问了一个问题，传给大模型的，真的只有你这句话吗？
  >
  > 答案显然不是。
  >
  > 你按下回车之前，Agent 已经帮你组装好了一大段文本。最前面是系统提示词：你是谁、能做什么、不能做什么、输出要什么格式。任何一个 Agent 都有系统提示，而且往往很长，不同 Agent 写得也不一样。
  >
  > 系统提示后面，接着是技能列表。大部分通用 Agent 会在用户目录下的 agents/skills 文件夹里放技能。它会扫描这个目录，把所有技能的描述拼成一段话——相当于告诉模型：这台电脑上有这些技能，它们大概是做这些事的。模型看到之后，再判断你的问题要不要加载某个技能。MCP 服务也类似，它的工具说明会在开头就被注入进去。
  >
  > 接下来还有工作区下Agents.md文件的内容，获取全局记忆内容，Agent会把这写markdown文本也拼接进来。不同Agent的拼接方式不一样。
  >
  > 所以，你问的可能只是一句不到 100 个 token 的话，真正发到大模型那里的请求，可能已经接近一万、甚至十万个 token。你的问题，只是这本笔记本的最后一页；前面几页，是 Agent 提前写好的。
  >
  > 这也是我推荐大家把 DeepSeek Harness 当日常 Agent 工具的原因：它插件很多、很开放，还把整个上下文组装过程摊开给你看。系统提示、技能、工具、历史，每一层都能看到。看多了你就会明白：我们现在能控制大模型的唯一方法，就是提示词，也就是文本；而 Harness，本质上就是一个提示词组装器——不停地组装文本、发给模型、接回文本，再去执行动作。
  >
- **事实/口径**：实际请求通常由 system prompt、工具 / 技能 / MCP 描述、历史消息、检索或文件内容、当前用户消息组成，顺序和策略因 Harness 而异；技能描述注入的是“目录 / 说明”，完整技能内容通常在模型决定加载后才读入。token 量级（<100 → 1 万–10 万）是示意，取决于系统提示长度、技能与 MCP 数量、历史长度。DSH 的轨迹 / 上下文面板可以查看组装结果；“只有 DSH 能看”不成立，其他 Harness 也有调试入口。
- **素材**：输入框、组装台、纸层、token 计数器；`dsh-desktop.png`、`dsh.png`；新增 10`dsh-context.png`（DSH 上下文 / 轨迹面板，自截，待补）。

## S23 · skills — 技能不是越多越好

- **时长**：120s
- **一句话论题**：技能目录本身会占用上下文；只留真正有用的，过时的要淘汰，需要时再点名加载。
- **屏幕文字**：少而精 / 按需点名 / 会过时；superpowers 30 万星 → 已淘汰；推荐 grill-me；huashu design
- **画面**：左边一个塞满几百个 skill 的目录树，用一个放大镜扫描一下，指引生成一个很长的文本。这个文本生成完之后，插入到一个聊天窗口里面。这个聊天窗口就是 Agent 内部的聊天页面，就变成了一个很长的提示词，这里主要演示skill目录组装的过程，会把这个提示词拉长，这个画面底下是一个 token 的虚拟数字码。这个技能目录插进这个 Agent 的内部聊天界面后，token 量就从一个数字跃迁到另一个数字，相当于这个技能目录导致了 token 的增长。然后切换到另外一个新场景，就是下方一条时间轴：2026.03 superpowers 走红 （上面放置一个GitHub星标趋势曲线）→ 2026.07 社区开始讨论卸载 （时间轴上面放一个讨论页面的截图）→ 2026.11 常驻只剩 grill-me（这里可以放一个 skill 目录下的“灵犀”这个技能）。场景接着把这个时间轴往左退场，退场完之后：显示一个Agent的聊天对话框，然后在聊天框里面能看到用户输入/grill-me,在动画里面就模拟出 Agent 开始问一些问题（Q1、Q2、Q3），接着你读出对这些问题的回答，最终形成一个非常完善的计划网上的计划文件写在右半边。接着,将右半边的这个计划文件缩小成一个文档，放到左半边的 Agent 对话框里面，然后模拟演示 Agent 开始干活。这主要是为了让右半边让出位置,然后右半边出现“huashu design”这个技能，并将“huashu design”的一些效果图片展示在页面上。
- **动画**：参考上面的画面。
- **分镜节拍**：参考上面的画面
- **旁白**：

  > 说到技能，有些人特别喜欢装一大堆，刚刚提到，agent在会话开始，会把你目录下技能拼接为一个目录给到大模型，你电脑上的技能越多，Agent 就要生成越长的技能目录；这个目录本身会占上下文，很多时候是没用的内容。
  >
  > 我的做法是：只装真正有用的。有些技能，我甚至放到 Agent 正常搜不到的地方；等我用到它的时候，再给一个确切目录给agent：“你就用xxx目录下这个技能来执行。” 常用的、确实每天都要用的，才放进常驻目录。
  >
  > 随着AI的快速迭代，一些原本好用技能会变得没那么好用或者没必要的。2026 年 3 月，有一个技能特别火，叫 superpowers，GitHub 上三十多万星。那时候 AI 的编程能力还不够强，大家需要它来规范 AI 的编程流程。但模型能力上来之后，执行 Agent 任务基本不需要这种约束了，所以它已经从我的常驻技能里淘汰了。那几个月很火的那批技能，大部分今天都不太适用了——这个领域就是这样，日新月异。
  >
  > 我现在在编程上唯一保留的技能，是 grill me。需求不清楚的时候，我会用它来跟我一起盘问、确认，把问题问清楚再动手。
  >

## S24 · model-choice — 先选对模型

- **时长**：110s
- **一句话论题**：模型分多模态和非多模态；要读图、做 PPT，就必须选多模态。
- **屏幕文字**：多模态 / 非多模态；看图 / 读视频 / 截图自检；DeepSeek-V4.1 flash、Qwen3.8-Max、GLM-5.3-Flash；GLM-5.3 非多模态
- **画面**：一张“模型货架”，多模态一排、非多模态一排，模型卡带文字标签和已有的 DeepSeek / Qwen Logo。再切一个 PPT 生成场景：分左右两部分，左边这部分代表带多模态模型的，右边这部分是非多模态模型的生成过程，两个场景一起执行，一开始两边都一样，都是通过编写代码来生成这个 PPT。区别在于第二步：1.多模态模型：生成完之后开始截图，通过视觉来检验是否有冲突。2.非多模态模型：只能查看代码，自己猜测是否有冲突或者需要调整。再切到一个新页面，展示两种模型：一种是生图模型，一种是生视频短剧模型。这里需要去网络上找一点素材，把生图模型生成的图和短剧模型生成的短剧展示出来
- **动画**：参考上面的画面。
- **分镜节拍**：参考上面的画面

| 节拍 | 时间     | 画面                                 | 旁白落点                          |
| ---- | -------- | ------------------------------------ | --------------------------------- |
| 1    | 0–25s   | 眼睛 vs 纯文字两个入口               | 模型先分两类：多模态、非多模态    |
| 2    | 25–55s  | PPT 生成 → 截图 → 视觉检查 → 重排 | 做 PPT 必须多模态，才能自己看截图 |
| 3    | 55–85s  | 模型货架：国产多模态 / 非多模态      | 国产型号举例；多模态不等于更聪明  |
| 4    | 85–110s | 生图 / 生视频货架快速扫过            | 还有两类专门模型，知道存在就好    |

- **旁白**：

  > 这里补充一个容易被忽略的技巧：选对模型。任务开始的时候，先确认这个模型适不适合你的任务。
  >
  > 现在的模型很多，但无非两类：多模态，和非多模态。多模态可以识别图片，甚至能解读视频；非多模态只能处理文字。如果你要做一套精美的 PPT，或者需要它解读图片、看设计稿，就一定要选多模态模型。因为现在能力强的 Agent 做完 PPT 会自己截图，让视觉模型检查有没有元素干涉、文字和图片有没有重叠。你选一个非多模态模型，就算他的编程能力比较强，但是他无法检查做完的这个 PPT 在视觉上是否好看或者有干涉，他只能通过代码来评估。
  >
  > 国产这边，DeepSeek-V4.1 flash、千问 3.8 Max、GLM-5.3-Flash 都是多模态；GLM-5.3 这个旗舰则是非多模态，偏文本和 Agent 任务。国外主流旗舰，像 GPT、Claude、Gemini，基本都已经是多模态，差别更多在能力侧重和价格。注意，多模态不等于更聪明；纯文本任务上，非多模态模型可能更强，也可能更便宜。
  >
  > 另外还有两类专门的模型。生图模型，比如 GPT Image、Midjourney、Seedream；生视频模型，比如字节的 Seedance、快手的可灵、Google 的 Veo、OpenAI 的 Sora。平时刷到的那些短剧，很多就是 Seedance 这类模型生成的。现在很多 Agent 的工具也可以集成图片生成模型和视频生成模型。在有些任务里面，可以让生图模型直接生成你需要的图片，而不是通过 AI 写代码来生成图片。
  >
- **事实/口径**：截至 2026-11：DeepSeek-V4.1 flash 为 552B MoE、8B 激活、原生多模态；Qwen3.8-Max 为 2.4 万亿参数 MoE、95B 激活、支持视觉理解；Qwen3.8-Flash 是轻量多模态；GLM-5.3-Flash / FlashX 属视觉理解模型，GLM-5.3 是文本旗舰。GPT、Claude、Gemini 的主流版本基本都支持多模态。型号、参数和价格月月变，讲课前复核。生图：GPT Image、Midjourney、Seedream（字节）、GLM-Image；生视频：Seedance 2.x（字节，统一音视频联合生成，支持文 / 图 / 音频 / 视频输入）、可灵（快手）、Veo（Google）、Sora（OpenAI）。短剧用 Seedance 是举例，不声称全部。
- **素材**：眼睛 / 文字图标、模型卡、PPT 自检 mock；`./素材/logo/deepseek.png`、`./素材/logo/qwen.png`；GLM 用文字卡，不新增 Logo；生图 / 生视频只做文字货架，不堆 Logo。

## S25 · slash-commands — 斜杠后面的三个命令

- **时长**：85s
- **一句话论题**：输入框不只是聊天框；/init 建记忆、/go 定目标、/plan 先审计划再动手。
- **屏幕文字**：/init /go /plan；初始化 / 目标 / 计划
- **画面**：一个输入框，打出“/”，弹出一个命令面板；三个命令依次高亮，每个命令旁边展开一个小场景：/init 是空目录 → 扫描项目 → 生成 agents.md；/goal 是一条长任务清单，AI 循环推进直到完成；/plan 是 AI 先写一份计划，用户审阅，旁边的“写文件”开关被锁住。
- **动画**：参考上面的画面。
- **旁白**：

  > 再说一个很多新手不知道的技巧：善用斜杠命令。很多用户，尤其是非编程领域的，一开始并不知道输入框里打一个斜杠，能叫出 Agent 的隐藏命令。大部分 Agent 工具都支持。
  >
  > 最常用的有三个。第一个，/init：给新项目生成 agents.md。它会用一套默认提示词，把项目读一遍，生成这个文件；老项目开始用 AI 开发，也可以用它来更新。第二个，/goal：goal，目标。任务很大、但目标很明确的时候，用它让 AI 不停迭代，直到完成。第三个，/plan：计划模式。有些 Agent 是按钮，有些是斜杠命令。它让 AI 先写计划、你来审；这时候它不会做任何写操作，你确认之后，它才开工。任务比较大，或者你自己也没想清楚要做到什么程度，就先 /plan，能省掉很多返工。
  >
- **事实/口径**：斜杠命令的名称和入口因产品而异：/init、/go、/plan 是常见形态，不保证每个 Agent 都有；有的产品把计划模式做成按钮。DSH、Claude Code、Cursor 等各有自己的命令集合，以实际版本为准。“/plan 只写计划、不做写操作”是常见行为，但不同产品的边界不完全一样。

## S26 · task-scope — 把 0 到 100 切成三段

- **时长**：95s
- **一句话论题**：任务越大，细节丢得越多；切开做，再回头复盘，比一口气冲到底稳。
- **屏幕文字**：0 → 100；0–35 / 35–70 / 70–100；开发 → 评审 → 修复
- **画面**：一条从 0 到 100 的长条，AI 从 0 冲到 100，但中间稀稀疏疏一些格子空了、变灰；回放时，空掉的格子被高亮。然后同一条长条被切成三段，每段单独执行，格子被填满。还有一个进度是从 0~10、10~20，逐步分十步来推进。旁边要显示“号是9”这个字眼，代表这个分段过于细，不值得。

  还是以这个长条为例，切换到下一个场景。在切换过程中，3 个场景的 3 个条隐藏交集，或者汇总成一个长条。

  这个长条放在上半部分，颜色不一：有些是绿色的，有些是红色的，有些是黄色的。颜色不同代表有 bug 或者有缺陷。

  当 AI 在这个长条上干活时，会有一个箭头代表回去检查，然后会有一个放大镜扫描这个长条的内容。扫到红色或黄色，就会把它修复成绿色，逐渐把这个长条的缺陷给修复好。
- **动画**：参考上面的画面。
- **旁白**：

  > 使用Agent进行任务的时候，要把握任务范围的“度”。Agent 能完成你描述的任务，但任务写得太大，交付时你只能看到“100 到了”，中间丢了多少细节，你不一定知道。
  >
  > 如果任务是 0 到 100 的进度。一口气让它从 0 做到 100，Agent最终给你呈现的的确是100这个数字，但中途的细节就不好说了。更好的做法是切成三段：0 到 35、35 到 70、70 到 100。做 0 到 35 的时候，它只需要想这一段，细节会完整得多。
  >
  > 但也不能切得太碎。切成十段、二十段，时间成本也是成本，没有必要。这个“度”没有标准答案，要看你用的 Agent、搭配的模型，还有你自己的经验。
  >
  > 另外，如果你 token 比较富裕，我建议每做完一段，让它回头评审一下：刚才哪里做得不好、架构有没有埋雷、有没有遗漏的 bug，再针对评审结果修。开发、评审、修复，再开发、再评审——就像我们做完一个项目要复盘一样。只往前走、不回头看，问题会一直留在里面。
  >
- **事实/口径**：0–100 是示意，不是精确方法；分段粒度取决于模型能力、上下文窗口、任务耦合度和你的预算。强耦合的任务切太碎，沟通成本反而上升；评审 / 复盘会额外消耗 token，是否做看预算。没有一套对所有人都最优的粒度。
- **素材**：长条、格子、分段标尺、复盘印章；纯自绘。

## S27 · secrets — 有些东西，不能交给 Agent

- **时长**：100s
- **一句话论题**：你给 Agent 的每一段文字都可能离开你的电脑；密码、API key、身份证和公司机密，不要放进去。
- **屏幕文字**：不能给：密码 / API key / 身份证·银行卡 / 公司机密 / 客户数据；会给出去：上下文 → 模型服务商 → 日志 / 插件 / 技能
- **画面**：一个输入框，用户粘贴一串 `sk-...`，画面立刻变红，显示个叉；旁边一条数据流向图：输入框 → Harness 上下文 → 模型 API（云上）→ 可能的日志 / 缓存；再分叉到第三方 Skill / MCP。下方五张“禁止入内”卡片：密码、API key、身份证 / 银行卡、公司机密、客户数据。最后翻出正确做法卡：环境变量 / 密钥管理器、脱敏裁剪、最小权限、人工审批。
- **动画**：粘贴 → 红色警告 → 数据流箭头一路亮向“外部”；五张卡片依次盖上“禁止”；正确做法卡翻出，颜色从警示红转回纸面色。
- **分镜节拍**：

| 节拍 | 时间     | 画面                                        | 旁白落点                         |
| ---- | -------- | ------------------------------------------- | -------------------------------- |
| 1    | 0–20s   | 粘贴 API key，画面变红                      | Agent 不是只在你电脑里自说自话   |
| 2    | 20–50s  | 数据流：上下文 → 模型服务商 → 日志 / 插件 | 你贴进去的东西，可能发到外面     |
| 3    | 50–80s  | 五张“禁止入内”卡依次盖下                  | 密码、key、证件、机密、客户数据  |
| 4    | 80–100s | 正确做法卡：环境变量、脱敏、最小权限        | 能不给的就不给；要给也给最小必要 |

- **旁白**：

  > 最后必须讲安全。这一页是给所有新手的：有些东西，绝对不能交给 Agent。
  >
  > 你要先建立一个概念：Agent 不是一个只在你电脑里自说自话的程序。你发给它的每一段文字，都会进入上下文，然后被发到模型服务商那里；它可能被记录、被缓存，也可能经过你安装的插件、技能、MCP 服务。也就是说，你贴进去的东西，是可能“发到外面”的。
  >
  > 所以，这几类信息不要给：密码、验证码；大模型的 API key、云服务的密钥；身份证、银行卡、住址这些个人敏感信息；公司的机密文档、未公开的代码；还有客户的数据。尤其是 API key——它不是一句话，它是一把钥匙，别人拿到就能花你的钱、用你的额度。把 key 写进对话、写进 agents.md、写进 skill，都等于把它交出去。
  >
  > 正确的做法是：密钥放环境变量或密钥管理器，让程序去读，不要出现在提示词里；确实需要 AI 处理敏感数据，先脱敏、裁剪，只给它必要的那一部分；给它最小权限，能只读就不要给写权限。记住一句话：能不给的，就不给。
  >
- **事实/口径**：上下文会发送到模型服务商；是否用于训练、留存多久，取决于产品与设置（API、企业版、个人版的策略不同），不要说成“一定被用于训练”。第三方 Skill / MCP 可能读取并外发数据，安装前看来源。API key 泄露可能被盗刷，例子里的 key 用假串。建议：环境变量 / 密钥管理器、敏感数据脱敏裁剪、最小权限、高风险动作人工审批；这是风险教育，不构成对具体厂商的指控。
- **素材**：输入框、数据流图、五张禁止卡、正确做法卡；警示色用珊瑚红；`./素材/logo/dsh.png` 可选。
